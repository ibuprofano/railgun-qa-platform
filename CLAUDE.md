# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

This repository is Gonzalo Roland's final project for an AI-driven software engineering course (AI4Devs, LIDR). It is a standalone repository: until the final submission the project lived in a `finalproject-GR/` subfolder of the course fork, and its history was carried over.

The product being designed and built is the **QA Automation Platform**: a multi-tenant B2B web app for QA teams to author test cases (Gherkin or manual), organize them in folders, run them in batched "executions" with a defined lifecycle, track bugs tied to failing runs, and report on project health via dashboards and exports. Full behavioral spec: [PRD.md](PRD.md).

## Current state: MVP complete, full roadmap in progress

The MVP ([docs/roadmap-mvp.md](docs/roadmap-mvp.md)) is complete, and [docs/roadmap-full.md](docs/roadmap-full.md) is the active roadmap, built slice by slice as OpenSpec changes (`openspec/changes/archive/` holds every finished one). What exists:

- **Foundations:** RLS tenant isolation with separate migrator, API and worker roles; Clerk identity with provisioning on first sign-in; project-role and Owner guards; the same-transaction activity log; envelope-encrypted environment credentials with audited reveal.
- **Features:**
  - test cases (four-level folder tree, Gherkin, tags)
  - executions (full lifecycle, Cancel, Try Again with attempt history, history panel, live updates over SSE)
  - bugs (auto-creation on failure, tags)
  - projects and workspace settings, Project Settings › Environments
  - the Activity and Trash screens
  - the Overview, Test Cases, Executions and Bugs dashboards, with daily Health Score history
  - PDF reports for the Bugs, Executions and Test Cases dashboards
- **Not built yet:** invitations and members, image attachments and object storage, the Overview PDF and the per-execution HTML/PDF report, the traceability graph, the automated execution engine, deployment (hosting is open-questions.md E1–E4).

The schema lives in `db/migrations/` (`0001`–`0021`, each with `.up.sql` and `.down.sql`); `prisma/schema.prisma` holds only the datasource and generator. CI (`.github/workflows/ci.yml`) runs install, lint, typecheck, the report-font fetch, the database roles, every migration and the RLS coverage check on every push and PR; it does not run the test suites yet.

**Commands** (run from the repository root):
- `npm install` — installs every workspace.
- `npm run setup` — one-time local setup (`scripts/setup.js`), safe to rerun: checks Node and Docker; starts Postgres and waits for its roles; writes `apps/api/.env` and `apps/web/.env.local`, asking for the two Clerk keys (or reading `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`/`CLERK_SECRET_KEY` from the shell) and generating `SECRETS_MASTER_KEY`; migrates a fresh database and runs the RLS check; fetches the report fonts. It never overwrites a value already set, and on an already-migrated database it skips migrations (see "Existing dev databases").
- `npm run dev` — starts the API and web dev servers and the background worker together in one terminal (`scripts/dev.js`, output prefixed `[api]`/`[web]`/`[worker]`; Ctrl+C stops all three). Postgres must already be up (`docker compose up -d`).
- `npm run dev -w apps/web` — Next.js dev server (`localhost:3000`).
- `npm run dev -w apps/api` — NestJS dev server (`localhost:3001`; `GET /health`).
- `npm run fonts -w apps/worker` — one-time: downloads the report fonts (Noto Sans JP, Noto Sans Mono CJK JP; ADR 0026/0027) into the gitignored `apps/worker/fonts/` and verifies their SHA-256. Without them the worker starts but every report ends Failed ("Report fonts are not installed"). `REPORT_FONTS_DIR` overrides the folder.
- `npm run dev -w apps/worker` — the background worker alone (Graphile Worker, [ADR 0018](docs/adr/0018-queue-library.md)): runs queued jobs (`report_generate`) and two daily ones, `health_snapshot` (00:15 UTC) and `trash_purge` (03:00 UTC). It connects as `railgun_worker`.
- `npm test -w apps/api` — Jest/Supertest tests for the API, against the docker-compose database. They need `SECRETS_MASTER_KEY` set in the shell, since tests never read `.env` (any valid key works, e.g. a fresh `openssl rand -base64 32`).
- `npm test -w apps/worker` — Jest tests for the worker, against the docker-compose database. `graphile-worker` is ESM-only, so the script runs Jest through `node --experimental-vm-modules` (call `npm test`, not `npx jest`). The `trash_purge` job test ("runs as the trash_purge job") is known to be flaky, failing about one run in three; rerun it alone before treating a failure as real.
- `npm run test -w apps/web` — Vitest/React Testing Library tests for the web app.
- `npm test -w packages/reporting` — Vitest tests for the shared metrics, chart and report-data package. Run `npm run build -w packages/reporting` after changing it: the API and worker import its built output.
- `npm run lint` / `npm run typecheck` — the root scripts already wrap `--workspaces --if-present`, so this runs across every workspace that defines the script and skips the placeholders that don't; append `-w <workspace>` (e.g. `npm run lint -w apps/api`) to scope to one. Running `npm run lint --workspaces` directly (bypassing the root script) fails hard on any workspace without a `lint` script — use the plain `npm run lint` form.

**Environment variables.** `apps/api` loads `apps/api/.env` if present (`src/load-env.ts`, Node's built-in `process.loadEnvFile` — no dotenv dependency); `apps/web` loads `apps/web/.env.local` (Next.js). Both files are gitignored; `apps/api/.env.example` lists the API's variables. Anything already set in the shell still wins. Tests never load these files. `npm run setup` creates both files; by hand: copy `.env.example` to `.env`, paste the same `CLERK_SECRET_KEY` as `apps/web/.env.local`, and generate a `SECRETS_MASTER_KEY` once — then keep it, since workspace data keys (and every stored environment password) are wrapped with it.
- `DATABASE_URL` — optional; falls back to the docker-compose Postgres (`postgresql://railgun_app:app_dev_password@localhost:5433/railgun`).
- `REALTIME_DATABASE_URL` — optional for `apps/api`; the connection the live-updates listener (`src/realtime/live-events.service.ts`) `LISTEN`s on, defaulting to `DATABASE_URL`. `LISTEN/NOTIFY` doesn't work through a transaction-mode pooler, so in production this must be a **direct, non-pooled** connection as `railgun_app` (ADR 0005), even when `DATABASE_URL` goes through a pooler.
- `CLERK_SECRET_KEY` — required for every authenticated API request (ADR 0002) — without it the API rejects every token with 401 and warns at startup. Currently the temporary dev Clerk app's key (see `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` below), set in both `apps/api/.env` and `apps/web/.env.local`. As of [frontend-bootstrap](docs/roadmap-mvp.md), also read server-side by `apps/web`'s `proxy.ts` (Clerk's route protection).
- `SECRETS_MASTER_KEY` — **required** as of [secrets-encryption](docs/adr/0004-secrets-storage.md): a 32-byte key, base64-encoded (e.g. `openssl rand -base64 32`). Unlike `DATABASE_URL`, this has no fallback and fails fast at first use if missing or the wrong length (`EnvKeyProvider`, `src/common/key-provider.ts`) — deliberate, since a silent default for a master encryption key would be a real vulnerability, not a dev convenience. Sign-up (`provisionIdentity`) now provisions a workspace DEK and needs this set to succeed.
- `WEB_ORIGIN` — optional; the CORS origin `apps/api` allows, defaults to `http://localhost:3000` (`main.ts`). Only matters for local dev — production CORS origin is a deployment-time decision (open-questions.md E1–E4), not yet made.
- `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` — **required** for `apps/web` as of [frontend-bootstrap](docs/roadmap-mvp.md): Clerk's publishable key, needs a real Clerk account to exist (same posture as `CLERK_SECRET_KEY` above). **Currently set via `apps/web/.env.local`** (gitignored, not committed), provisioned by `npx clerk@latest init` — a *temporary* dev-only Clerk app with no real account behind it. This is a stopgap so the app is demoable now; replace it with a real Clerk account's keys before any real/graded demo, since this temporary app and its keys can be revoked or expire without notice. Without a valid key, Clerk's hosted `<SignIn>`/`<SignUp>` components and `ClerkProvider` have nothing to talk to.
- `NEXT_PUBLIC_API_URL` — optional for `apps/web`; the base URL its API client targets, defaults to `http://localhost:3001` (matching `apps/api`'s own default port).
- `WORKER_DATABASE_URL` — optional for `apps/worker`; defaults to the docker-compose Postgres as `railgun_worker` (`postgresql://railgun_worker:worker_dev_password@localhost:5433/railgun`). Never point it at the migrator role.

**Database roles and the job queue.** Four roles, all created by `db/init/` on a fresh volume:
- `railgun_migrator` owns everything and runs migrations;
- `railgun_app` is the API's role: no ownership, no RLS bypass;
- `railgun_worker` is the worker's role: same posture, plus only what migrations grant it explicitly — `0014` (the queue schema, delete and select on the trashable tables, insert into the activity log, workspace ids), `0017` (`health_snapshot`, select on `test_run`), `0019` (`report`, insert into `report_file`, select on `tag` and `bug_tag`) and `0020` (select on `test_run_attempt` and `test_case_tag`). A new worker query on another table needs its own grant in a migration;
- `railgun_breakglass` is inert.

The API enqueues jobs only through `enqueue_job(task, payload, run_at)` inside its own transaction; the task name must be on that function's allow-list. `npm run db:migrate` installs Graphile Worker's `graphile_worker` schema (`scripts/install-job-queue.js`) before the SQL files. **A dev database created before `background-jobs` needs a one-time catch-up**:
1. `DATABASE_URL=postgresql://postgres:postgres@localhost:5433/railgun node scripts/apply-sql.js db/init/02-worker-role.sql`
2. `DATABASE_URL=postgresql://railgun_migrator:migrator_dev_password@localhost:5433/railgun node scripts/install-job-queue.js`
3. Apply `db/migrations/0014_background_jobs.up.sql` as `railgun_migrator`, the same way as any other new migration on an existing database.

**Reports** ([ADR 0027](docs/adr/0027-report-storage-and-delivery.md)): `POST /projects/:id/reports` queues `report_generate`; the worker renders the PDF with pdfmake in a worker thread (30 s limit, ADR 0026) and stores it in `report_file` (Postgres, until object storage — E3); the requester downloads it from `GET …/reports/:reportId/file`. Reports expire after 7 days and the daily `trash_purge` deletes them. Report kinds are a registry: the names and labels in `packages/reporting/src/report-kinds.ts`, an options parser per kind in the API's `src/reports/report-rules.ts` and a builder per kind in the worker's `src/reports/kinds.ts`, each typed `Record<ReportDbKind, …>` so a new kind can't miss one. Kinds today: `bugs-dashboard`, `executions-dashboard`, `test-cases-dashboard`.

**Existing dev databases.** `npm run db:migrate` reapplies every file and is meant for a fresh volume. On a database that already has the earlier migrations, apply each new one on its own as `railgun_migrator`: `DATABASE_URL=postgresql://railgun_migrator:migrator_dev_password@localhost:5433/railgun node scripts/apply-sql.js db/migrations/<file>.up.sql`.

**Demo data.** `npm run db:seed -w apps/api -- --email <you@…>` (or `-- --clerk-user-id <id>`) fills that user's default project with the ShopFlow demo dataset: a folder tree of test cases, executions in every status, bugs, two teammates, and backdated history ([demo-seed](openspec/specs/demo-seed/spec.md)). The user must have signed in once. The seed is additive and idempotent: it never changes existing rows, and a rerun writes nothing. It needs `SECRETS_MASTER_KEY` (credentials are encrypted) and, for `--email`, `CLERK_SECRET_KEY`, both read from `apps/api/.env`.

**Dependency version notes** (discovered scaffolding this — all pinned below their breaking "latest" for ecosystem compatibility, not an oversight):
- **TypeScript pinned to `^6.0.3`**, not the current `7.x` — `ts-jest` and `typescript-eslint` both still declare a `<7`/`<6.1.0` peer range.
- **NestJS pinned to `^11.2.8`**, not `12.x` — NestJS 12 ships `"type": "module"` across every `@nestjs/*` package, which breaks Jest's CommonJS module loading outright.
- **Prisma CLI pinned to `6.19.3`**, not the current `7.x`/`8.0.0-rc` — Prisma 7 removed the `url` property from the `datasource` block entirely (connection config moves to `prisma.config.ts` plus a mandatory driver `adapter`), which has direct implications for [ADR 0008](docs/adr/0008-tenant-context-implementation.md)'s `withTenantContext` design and needs a deliberate evaluation, not a drive-by fix. Still pinned; upgrading is its own change.
- **`@hookform/resolvers` pinned to `5.9.2`**, not the current `6.0.0` — `6.0.0`'s own optional peer chain is internally broken (`@typeschema/effect` requires `effect@^3.6.8` while `@hookform/resolvers` itself wants `effect@^4.0.0`), which fails `npm install` outright even though `effect`/zod are unrelated to what this project actually uses. `5.9.2` is the last version before that break and is the first to explicitly declare `zod: "^3.25.0 || ^4.0.0"` as a peer, matching the `zod@^4` actually installed.
- **Postgres must be ≥ 15** (docker-compose runs 16) — as of `execution-lifecycle`, migration `0008` uses `ON DELETE SET NULL (column)` on composite tenant FKs, which clears only the referenced id and keeps `workspace_id` intact. Keep this in mind when hosting (open-questions.md E1–E4) is chosen.
- **Node must be ≥ 22.18** as of `background-jobs`: `graphile-worker` 0.18 requires it, and CI runs Node 22. It is ESM-only and is loaded from CommonJS code through Node's `require(esm)`.

## Two roadmaps, one target architecture

[docs/roadmap-mvp.md](docs/roadmap-mvp.md) and [docs/roadmap-full.md](docs/roadmap-full.md) describe two build orders for the *same* architecture, not two different designs. The MVP roadmap cuts feature breadth (folders, tags, invitations, SSE, the job queue, image attachments, dashboards/reports) because those are additive later — new columns, tables, or screens over data already shaped correctly. It never cuts anything structural (RLS/tenant context, same-transaction activity logging, the full membership/authorization schema, envelope encryption for secrets, soft-delete columns, the execution state machine) because retrofitting those after features and data exist is the expensive path. The MVP is complete, so [docs/roadmap-full.md](docs/roadmap-full.md) is the active roadmap: check its phase and slice entries before assuming a feature is in scope.

## Architecture

Settled in [ADR 0001](docs/adr/0001-tech-stack.md) and amended by ADRs 0002–0027. Built as described below, except where a bullet says otherwise:

- **Monorepo ([ADR 0010](docs/adr/0010-monorepo-layout.md)):** npm workspaces (not pnpm — the repo already runs plain npm), `apps/web` (Next.js, App Router), `apps/api` (NestJS), `apps/worker` (Graphile Worker tasks and the PDF render thread), `packages/shared-types` (still an empty placeholder), `packages/reporting` (dashboard metrics and their SQL, Health Score and test case health rules, chart geometry and SVG, each report's data — shared by the API, the worker and the web, [ADR 0023](docs/adr/0023-chart-rendering.md)), `packages/config`. The DB schema lives in `db/migrations/`. No Turborepo/Nx yet — plain per-workspace npm scripts are enough at this app count.
- **Database:** PostgreSQL, single shared schema. Every tenant table carries `workspace_id`, denormalized onto deep children. No Redis in v1.
- **Tenant isolation ([ADR 0003](docs/adr/0003-tenant-isolation.md), mechanism in [ADR 0008](docs/adr/0008-tenant-context-implementation.md)):** two layers — Postgres RLS (policy: `workspace_id = current_setting('app.workspace_id')`, forced, fails closed with zero rows if unset) as the backstop, plus an explicit `withTenantContext(prisma, workspaceId, fn)` transaction helper that every request/job must go through. Services are injected a `Prisma.TransactionClient`, never the bare `PrismaClient`. This is the single most important invariant in the codebase — a missing tenant scope is the highest-impact failure mode this product has.
- **Auth ([ADR 0002](docs/adr/0002-authentication-and-workspace-membership.md)):** Clerk for identity only (sign-up, sign-in, sessions, password reset, email verification). Workspaces, project membership, roles, and invitations live entirely in our own Postgres — Clerk Organizations are explicitly *not* used, because invitations in this product are project-scoped and need semantics (accept/decline, 7-day expiry, resend to an existing member) Clerk's org-invite model doesn't support.
- **API transport ([ADR 0009](docs/adr/0009-api-authentication-transport.md)):** bearer token (Clerk session JWT, verified against Clerk's JWKS), not cookies — required because the frontend (Vercel, random per-PR preview URLs) and API (Railway/Render) are on different hosts.
- **Authorization:** two-level RBAC — workspace role (Owner/Collaborator) is a ceiling, project role (Admin/Contributor/Viewer) governs day-to-day access. One NestJS guard/policy module evaluates both; Owners are implicit Project Admin everywhere.
- **Secrets ([ADR 0004](docs/adr/0004-secrets-storage.md)):** application-level envelope encryption (AES-256-GCM), per-workspace data encryption key, wrapped by a master key (hosting secret store now, cloud KMS later via a swappable `KeyProvider`). Environment credentials are recoverable and revealable (audited); integration tokens and AI keys are write-only.
- **Real-time ([ADR 0005](docs/adr/0005-realtime-and-background-jobs-v1.md)):** server-sent events, one multiplexed stream per project (`GET /projects/:projectId/events`), with polling as the fallback when the stream is down. Events carry only identifiers — they're hints, not state; the client always refetches. Fan-out via Postgres `LISTEN/NOTIFY`.
- **Background jobs ([ADR 0005](docs/adr/0005-realtime-and-background-jobs-v1.md)):** a Postgres-backed queue (Graphile Worker, [ADR 0018](docs/adr/0018-queue-library.md)), enqueued in the same transaction as the triggering change. The execution lifecycle itself is a domain state machine persisted in the DB — the queue never owns lifecycle state.
- **Activity log ([ADR 0007](docs/adr/0007-activity-log-and-trash-purge.md)):** one append-only `activity_entries` table, no foreign keys (so it survives purges), written via `ActivityLogger.log(tx, …)` in the *same transaction* as the change it records. Immutability is enforced by revoked `UPDATE`/`DELETE` privileges plus a trigger, not by convention.
- **Trash / soft delete ([ADR 0007](docs/adr/0007-activity-log-and-trash-purge.md)):** top-level entities carry `deleted_at`/`deleted_by`; a daily job purges anything deleted >30 days, in dependency order, without ever touching the activity log.
- **Reports ([ADR 0006](docs/adr/0006-report-generation.md), [ADR 0026](docs/adr/0026-report-rendering-library-and-fonts.md), [ADR 0027](docs/adr/0027-report-storage-and-delivery.md)):** generated by the worker from one allow-listed data object (no secrets, no trashed items), built with the same functions the screen uses so a PDF matches its dashboard. PDF via pdfmake (no headless browser) with Noto fonts; charts drawn once as SVG and shared between the screen and the PDF. The HTML export (server-side template) arrives with the per-execution report and isn't built yet.
- **Frontend UI ([ADR 0011](docs/adr/0011-frontend-ui-stack.md)):** Tailwind CSS v4 (Next.js's current, Turbopack-supported path) with CSS Modules as the fallback; shadcn/ui (Radix primitives, copied into the repo via its CLI, not an opaque dependency) for modals/dropdowns/pickers; TanStack Query for data fetching, caching and mutation-driven invalidation, with SSE events invalidating queries; react-hook-form + zod for forms. Drag-and-drop is dnd-kit with in-house fractional keys ([ADR 0014](docs/adr/0014-drag-and-drop-and-ordering.md)); charts are the in-house SVG module, no chart library ([ADR 0023](docs/adr/0023-chart-rendering.md)). Only the traceability graph's library is still undecided (open-questions.md F6).

## Key domain concept to keep straight

The **Test Execution lifecycle** (`Draft → Ready → InProgress ⇄ Paused → Completed → Done/Canceled`, PRD §6.3.4) is the architectural center of gravity. It's a transactional domain state machine, not queue-driven ([ADR 0005](docs/adr/0005-realtime-and-background-jobs-v1.md): "the queue never owns lifecycle state"). Two behavioral requirements from PRD §6.3.3 drive its design: the elapsed timer counts only while `InProgress` (paused time excluded), and each run snapshots its test case's name and Gherkin script at the moment the execution starts, so later edits or deletes don't change run history. The schema is migration `0008` (`test_execution`, `test_run`, with `elapsed_ms_accumulated`/`last_resumed_at` for the timer and snapshot columns), with completion and sign-off rules in [ADR 0012](docs/adr/0012-execution-completion-and-sign-off.md), Cancel in [ADR 0019](docs/adr/0019-execution-cancel.md), Try Again and `test_run_attempt` in [ADR 0020](docs/adr/0020-execution-try-again.md), and history and Draft run changes in [ADR 0021](docs/adr/0021-execution-history-and-draft-run-changes.md).
